AGENTS SDLC PIPELINE REVIEW COMMENTS - MR !4 B1/B2 Memory Pipeline
Reviewer scope: Sujit Kumar Raul / ServiceForge, merge request !4 only.
Note: These comments cover agent workflow, memory design, orchestration, rules, skills, audit evidence, and quality gates. Code-level comments are in CODE_REVIEW_COMMENTS.txt.

Overall SDLC/pipeline summary
- This MR is a meaningful step toward adding memory to the ServiceForge agentic workflow. The repo now has a B1 memory design, a B2 feature spec, a retention rule, a memory retrieval skill, test evidence, and an audit report.
- The work shows good understanding that semantic memory already lives in instructions/rules and that episodic memory needs a separate store.
- The main pipeline issue is that the design describes a fuller architecture than the implementation actually delivers. That is fine for an assignment slice, but the docs need to be more explicit about what is prototype, what is approved contract, and what is still future work.

pipeline/feature2/memory-design.md
Purpose: B1 memory architecture design.

Architecture / correctness
- Medium: The design is clear on semantic, procedural, episodic, and working memory tiers. That is a good framing.
- Medium: The design says the write path is a non-blocking post-turn event hook, but this MR implements manual CLI scripts. That gap is okay, but it should be labelled as future work in the design or status changed from Proposed to Prototype Slice.
- Medium: The design mentions hybrid recency/relevance ranking and summarization, but the implementation uses FIFO trimming only.
  Recommendation: add a section called "Implemented in B2" and another called "Deferred" so reviewers do not have to infer the gap from the audit report.

Security
- Medium: The design talks about namespace isolation, but not about secrets in memory. Add a clear rule that credentials, tokens, customer data, and raw logs must never be retained.

Workflow/orchestration
- Medium: The design does not yet say exactly where in BA -> Developer -> Tester memory is read or written.
  Recommendation: define read-before-decision and write-after-validated-decision points for each agent.

Quality gates
- High: The design should require automated tests and secret scanning before a memory rule/store change can merge.

Testing/Observability
- Medium: Good that an audit report exists. Add a standard run-report location for future memory pipeline executions.

pipeline/features/feature-2-memory-pipeline.md
Purpose: B2 feature spec for memory pipeline scripts.

Architecture / correctness
- High: The spec has an internal contract mismatch. It says over-budget reads must use consolidation or importance weighting, then later says the approved behavior is FIFO oldest-entry removal. The implementation and tests use FIFO.
  Recommendation: update the Definition of Done and In Scope text to say FIFO is the approved B2 behavior, and leave summarization/importance weighting as future enhancement.
- Medium: The spec says the read path accepts a namespace and retrieval query/context. The script accepts namespace through MEMORY_NAMESPACE only and does not accept a query/context.
  Recommendation: either add the query argument or revise the spec to match the implemented CLI.
- Low: The feature status says Approved / implemented. That is okay if this is the CLI slice only, but not okay if readers interpret it as the full memory architecture.

Security
- Medium: Add an explicit DoD item that no secrets or raw telemetry are stored in memory.

Workflow/orchestration
- Medium: The spec describes scripts but does not update the main orchestration with when agents should call read/write.

Quality gates
- Medium: Tester results are included, which is good. CI should enforce the same command.

Testing/Observability
- Low: The Tester results section is useful and should be kept.

pipeline/feature2/rules/memory-retention-rule.md
Purpose: policy for what agents can store in episodic memory.

Architecture / correctness
- Medium: The discard/retain categories are sensible and easy to understand.
- Medium: The rule says over-budget memory must be summarized using hierarchical consolidation. Current read_memory.js drops FIFO instead. This is another contract mismatch.
  Recommendation: update this rule to say B2 uses FIFO for now, or implement the summarization rule.

Security
- High: The rule does not explicitly ban secrets, credentials, tokens, customer PII, or private telemetry.
  Recommendation: add those to the discard policy before agents start writing memory automatically.

Workflow/orchestration
- Medium: The rule says mandatory pre-storage filter, but the implementation allows any CLI caller to pass validated:true.
  Recommendation: define which agent/classifier approves a memory before write_memory.js is called.

Quality gates
- Medium: Add examples of allowed and rejected memory records so future agents have less room to guess.

Testing/Observability
- Medium: The tests cover several rejected terms. Add positive and negative examples for secrets and PII.

Pipeline failure modes to address
- Two agents writing memory at the same time can lose records.
- Runtime memory writes can dirty committed files.
- FIFO trimming can hide relevant memory without telling the caller.
- Docs say summarization/ranking in some places and FIFO in others.
- Agents may miss the memory retrieval skill because it is not in the canonical .claude/skills folder.
- Raw telemetry can leak internal workflow details.
- A caller can mark any payload validated:true without an independent classifier.

Prioritized SDLC fixes
1. Clean up duplicated sections in memory-retrieval-skill.md and memory-audit-report.md.
2. Align the memory design, retention rule, and feature spec with the actual B2 contract: FIFO CLI prototype, not full summarization/ranking.
3. Add CI for the memory tests.
4. Add no-secrets/no-PII/no-raw-telemetry language to the retention rule and memory skill.
5. Decide the official location for memory skill files and rule files, then update AGENTS.md and orchestration.
6. Add a run-report convention for memory writes/reads.
7. Document concurrency limits clearly before wiring this into automatic post-turn hooks.

Final pipeline note
- Good B1/B2 direction. The candidate has captured the right memory concepts and built a working CLI slice. Before merge, I would ask for cleanup and contract alignment so the next agent does not confuse the prototype with the full memory architecture.
