# Part A: Guardrail Design - Support-Ticket Refund Agent

| # | Guardrail Category | Specific Rule for this Agent | Trigger / Threshold |
| :--- | :--- | :--- | :--- |
| **1** | **Cost/token ceilings**[cite: 15] | Enforce a hard boundary on context size and reasoning cycles to prevent infinite self-correction loops on complex or noisy tickets. | **Trigger:** Halt execution and route to human if the agent exceeds 6 loop steps or if the incoming ticket text exceeds 1,500 characters[cite: 15]. |
| **2** | **Irreversibility checks**[cite: 15] | Restrict the agent's ability to execute actual payouts based on strict dollar boundaries to limit financial exposure. | **Thresholds:** <br>• *Safe:* $0 (Drafting apology/troubleshooting).<br>• *Conditionally-safe:* $1 to $50 (Auto-approves if matching KB policy)[cite: 15].<br>• *Never-safe:* >$50 (Agent drafts response but requires a human click to issue payout)[cite: 15]. |
| **3** | **Output sanitization**[cite: 15] | Ensure the generated customer response does not leak internal operations, KB policy text, or system instructions. | **Trigger:** Block the outgoing email if the response payload contains internal markers like "KB policy states," "System prompt," or raw JSON tool schemas. |
| **4** | **Prompt-injection defense**[cite: 15] | Treat the 300-character average ticket text as inherently untrusted[cite: 15]. The agent must never use the customer's text as authorization for a tool call. | **Trigger:** If ticket text contains command-style overrides ("ignore refund policy", "force approve") or requests amounts exceeding the $50 cap, execution is blocked and flagged for review[cite: 15]. |
| **5** | **Scope limits**[cite: 15] | The agent's permission boundaries must dynamically adjust based on the tenant's tier to prevent unauthorized payouts[cite: 15]. | **Threshold:** Free-tier tenants = Authorized for troubleshooting responses and $0 refunds only[cite: 15]. Enterprise tenants = Authorized for autonomous payouts up to the $50 cap[cite: 15]. |
