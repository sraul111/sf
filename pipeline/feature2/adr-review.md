## Findings
### Critical
None.

### Major
- **M1 — Resolve the buffered-window end boundary without changing booking semantics (carried over, refined).** The requirements contradict each other: requirements L31 (available "starting at 3:45pm") vs L55 (inclusive). L55 also justifies the inclusive rule as "consistent with how `TRAVEL_BUFFER_MINUTES` is applied in Feature 1's overlap check", and that is wrong. `bookJob` uses strict `isBefore` (`backend/src/main/java/com/serviceforge/service/TechnicianAvailabilityService.java` L40-L42). The Feature 1 decision amendment (`pipeline/decisions/feature-1-decisions.md`) says half-open, with "a booking exactly 45 minutes away is allowed". `Feature3DispatchControllerTest` L194 fixes `20:10` (exactly 45 minutes after `19:25`) as accepted, and the Verification in `pipeline/feature2/rules/no-overlap-booking.md` requires the same. The ADR defines a single `SchedulingWindowPolicy` interval used by both booking and parts (ADR L206, L273) without saying whether the end is inclusive. Plan Task 2 (L29) ties the policy's boundary tests to the Task 1 decision. **Impact:** (a) If the human chooses inclusive and the policy has one containment predicate, the result is one of two failures. Either booking changes, which breaks the Feature 1 and Feature 3 tests that must pass unchanged and violates the active rule, or the parts and booking checks disagree without anyone noticing. (b) With inclusive parts windows, two jobs for the same technician booked exactly 90 minutes apart are allowed by booking, yet their buffered windows touch at one instant. The peak-capacity check (ADR L210-L216) then counts both at that instant. Example: `VLV-BALL-075` has a total of 3; issuing 2 units to job A and 2 to job B returns `409`, even though the two holds never overlap in practice. **Correction:** Get the human decision. Correct the rationale in the requirement. Have `SchedulingWindowPolicy` expose the buffered bounds, with explicitly named predicates: booking-conflict stays half-open and unchanged, and parts-hold uses the approved convention. Have plan Task 2 state that booking behavior is unchanged whatever Task 1 decides. Add to plan Task 4 a back-to-back test with jobs exactly 90 minutes apart.
- **M2 — Define how local job times map to the injected clock (carried over, unchanged).** The design still compares `Clock.instant()` (ADR L256) with `LocalDateTime` job times that were seeded from the host clock (`MockDataStore.java` L32) or submitted through `datetime-local` (`technician-calendar.component.html` L26-L27). No zone is specified. **Impact:** the live in-use projection depends on the host zone and DST, and fixed-clock tests may not match production. **Correction:** Record a time contract. The simplest option that keeps the current API unchanged: compute "now" as `LocalDateTime.now(clock)`, treat the clock's zone as the contract (system default in the running app, fixed zone in tests), and document how DST gaps and overlaps are accepted. Apply the same conversion in the test setup.
- **M3 — Make the rebooking requirement implementable and verifiable (carried over, unchanged).** Requirements L56 requires the hold to follow an edited job. ADR L343 and plan L53 promise a rebooking test. `Job` start and end times are `final` (`Job.java` L10-L11). `MockDataStore` has no update operation, and Feature 3 deliberately kept `Job` immutable. Its assumption A1 and its out-of-scope list exclude edit endpoints (`pipeline/features/feature-3-dispatch-skills-and-parts-sku.md`). **Impact:** the plan's Task 4 acceptance check can't be met as written, and adding a mutation path changes the model (the migration-safety skill applies) and needs coordination with the inventory lock. **Correction:** The human decides. If editing is out of scope, change the requirement and plan to state explicitly that it is deferred, and prove only that windows are derived when needed (for example, two issues against jobs with different times). If editing is in scope, add a job-time update in `MockDataStore` under the same lock as the capacity check, go through migration-safety review, and re-check capacity for moved holds.
- **M4 — Restock/return semantics are narrower than the Definition of Done and are not raised as an open question (new).** The DoD (requirements L10) says restock/return is "immediately increasing its available quantity". Story 4 (L36) says available "increases by Q", and adds "*if* the restock corresponds to an active issue…", which implies a restock that doesn't correspond to one. The edge case at L57 limits returns by the "currently in-use quantity". The ADR allows only the return of a `(jobId, partId)` allocation. For an issue outside its window, "current availability was already unaffected" (ADR L218), so the total can't grow: `totalQuantity` is final and has no setter (ADR L271). Returns are also checked against *outstanding*, not *in-use*, quantity (ADR L218, L286). The traceability table (ADR L344) presents this as full coverage. **Impact:** (a) A return against a future or past issue doesn't increase current `Available`, so the DoD's "immediately increasing" fails. (b) A stock-in restock that isn't tied to an issue is impossible. (c) Under L57 read literally, every return against an inactive issue would be rejected, because its in-use quantity is 0. **Correction:** Add an ADR Open Question and a plan Task 1 item. Option (a): restock means only returning an issued allocation. Then change the DoD, Story 4, and L57 wording to "outstanding", and to "available increases when the hold is active at the time of the return". Option (b): restock can also add stock. Then `totalQuantity` can't be final, the reconciliation invariant has to allow a changing total, and the capacity check has to lock total updates too. Don't implement returns until this is decided.

### Minor
- **m1 — resolved** (see Status of Prior Findings).
- **m2 — Carry the promised concurrency test into plan acceptance checks (carried over, unchanged).** **Correction:** add to plan Task 4 a coordinated test where two requests compete concurrently for the last unit: exactly one returns `201`, the other `409`, and there is no over-allocation.
- **m3 — The existing Feature 1 component spec will break, and the plan doesn't say so (new).** `frontend/src/app/technician-calendar/technician-calendar.component.spec.ts` L30-L34 provides only a `TechnicianService` spy. When the component injects the new `PartsService` (plan Task 8), which depends on `HttpClient`, the spec fails with `NullInjectorError`. Plan Task 8 (L95-L101) and Task 9 (L113) don't list this change. **Correction:** list the spec change (provide a `PartsService` spy) as an expected artifact in Task 8, and state that it is the only existing test that changes.
- **m4 — The error-mapping mechanism and the wrong-owner status are not specified (new).** The existing convention maps `IllegalArgumentException` to `404` even for validation failures (`JobController.java` L30-L33; `TechnicianAvailabilityControllerTest` L230 `invalidTimeRangeReturnsNotFound`). The repo has no `@ControllerAdvice`, so `@Valid` failures don't produce an `ApiError` body. The ADR's error mapping (L284-L288) doesn't give a status for "job doesn't belong to the requesting technician" (requirements L51). **Correction:** specify dedicated exception types or controller-local `@ExceptionHandler`s in `PartController` so that `400` and `404` are distinct and both return `ApiError`. Don't use global advice: it would change `POST /api/jobs` error bodies, which Feature 3 excludes from scope. Choose and test a status for a wrong owner.
- **m5 — Lock scope, test clock, and test isolation (new).** `MockDataStore.jobs` is an unsynchronized `ArrayList` (L22). `save()` (L59-L62) writes to it outside the proposed inventory lock, while capacity and projection scans read every job, so a `ConcurrentModificationException` is possible. Spring Boot 3 turns off bean-definition overriding by default, so "a `Clock` bean that tests can override" (plan L49) needs `@TestConfiguration` with `@Primary`, or `@MockBean`. Issue tests change the singleton store, and `MockDataStoreFeature3Test` has no `@DirtiesContext`, so it shares a cached context. **Correction:** guard job reads and writes with the same lock or a thread-safe collection. Name the test-clock mechanism. Require `@DirtiesContext` (or equivalent reset) on Feature 2 tests that change state.
- **m6 — "Exactly one `45` literal" can't be checked as written (new).** Plan L29 doesn't limit the scope, and test code has to keep `assertEquals(45, …)` (`Feature3DispatchControllerTest` L235). **Correction:** limit the check to `backend/src/main/**`.
- **m7 — The displayed `Available` differs from the issuable quantity (new).** `GET /api/parts` reports availability at the current instant (ADR L256-L259), but issue capacity is the peak over the candidate window (ADR L210-L216). A user can see `Available 3` and still get `409` when issuing 2 for a future job. **Correction:** make the `409` `ApiError` message name the window and the maximum issuable quantity, and list this under the ADR's Negative consequences.

## Riskiest Decision

The riskiest choice is still deriving holds from job timestamps and checking peak-window capacity under a lock, now with one `SchedulingWindowPolicy` that booking and parts share. Centralizing the 45-minute constant is correct. Sharing a single *containment* predicate is not: booking is fixed as half-open by an active rule and by tests, while the parts requirement asks for an inclusive boundary. Unless the policy exposes both conventions explicitly, one of the two features ends up broken (M1).

## Required Changes

1. **M1:** Get the boundary decision and correct the incorrect "consistent with Feature 1" rationale in requirements L55. Give `SchedulingWindowPolicy` separate, named booking (half-open, unchanged) and parts-hold predicates. State in plan Task 2 that booking semantics are unchanged. Add a back-to-back test with jobs exactly 90 minutes apart.
2. **M2:** Record the time contract (for example, `LocalDateTime.now(clock)` with the clock's zone as the contract) in the ADR and use it in the test setup.
3. **M3:** Decide whether job editing is in scope. Either explicitly defer the rebooking edge case and change the Task 4 check, or add a locked job-time update that goes through migration-safety review.
4. **M4:** Add an Open Question on restock semantics (return-only vs stock-in) and align the DoD, Story 4, and L57 wording ("outstanding" vs "in-use"), or make the total mutable.
5. **m2:** Add the concurrent last-unit test to plan Task 4.
6. **m3–m7:** Update the component-spec provider, specify the exception mechanism and wrong-owner status, the lock scope and test-clock mechanism, and the scope of the `45`-literal check, and document the difference between window capacity and current `Available`.

## Questions for Human Review

1. At exactly `job.endTime + 45 minutes` (and at `startTime - 45`), is the part in use or available? (Booking stays half-open either way.)
2. Should technicians issue and return parts from the Angular screen, or is that API-only for Feature 2? (ADR Open Question 2)
3. Is job editing/rebooking part of Feature 2, or is the rebooking edge case deferred? (ADR Open Question 3)
4. Which time zone governs job timestamps and the inventory clock, and what should happen across DST transitions?
5. **New:** Does "restock" mean only returning an issued allocation, or can it also add stock to a part's total? Should a return against an inactive (future or past) issue count as satisfying "immediately increasing available"?
6. Can parts be issued only against `SCHEDULED` jobs, and what happens to outstanding issues when a job becomes `COMPLETED` or `CANCELLED`? (Carried over, still unaddressed.)
7. Should SKU matching be exact and case-sensitive, should the SKU appear in the parts table, and are the seed totals 3/10/5/3 acceptable? (ADR Open Questions 4–6; the ADR's provisional answers are reasonable.)
