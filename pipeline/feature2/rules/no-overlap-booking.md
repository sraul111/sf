# Rule — Overlap Appointment Fix

| Field | Value |
|---|---|
| **Constraint** | Two jobs for the same technician must never have overlapping time ranges, *and* must never be scheduled closer together than the standard 45-minute travel buffer. A new booking must be rejected with a conflict error if its `[startTime, endTime)` range overlaps *any* existing job's `[startTime, endTime)` range for that technician (not only when the new job's start time exactly equals an existing job's start time), **or** if it starts less than `TRAVEL_BUFFER_MINUTES` (45) minutes after an existing job's end time, **or** ends less than `TRAVEL_BUFFER_MINUTES` (45) minutes before an existing job's start time. |
| **Affected feature** | `pipeline/features/feature-1-technician-availability.md` (Feature 1 — Technician Availability Calendar) |
| **Related decision** | "standard travel buffer per job is 45 minutes" (`TRAVEL_BUFFER_MINUTES` in `TechnicianAvailabilityService`), from `pipeline/decisions/feature-1-decisions.md`. The fix must actually enforce this constant in the conflict check, not just avoid contradicting it — the constant currently exists but is never applied. |
| **Root cause (diagnostic)** | `backend/src/main/java/com/serviceforge/service/TechnicianAvailabilityService.java`, `bookJob(...)` — the conflict check only tests raw `[startTime, endTime)` interval intersection and never reads `TRAVEL_BUFFER_MINUTES`, so back-to-back bookings with less than 45 minutes between them (e.g. one job ending `20:00`, the next starting `20:23`) are silently accepted. This was already flagged as a known issue in the Feature 1 spec and decision log; not assumed to still be the exact code shape at fix time. |
| **Verification** | For a technician with an existing job `[16:23, 19:25)`, all of the following must be rejected with a conflict error: an identical range, a range that starts inside the existing one (e.g. `[17:24, 20:27)`), a range that fully contains the existing one, a range that ends inside the existing one, and a range that starts fewer than 45 minutes after `19:25` (e.g. `[19:40, 20:30)`) or ends fewer than 45 minutes before `16:23` (e.g. `[15:00, 15:50)`). A genuinely non-overlapping range that respects the 45-minute buffer on both sides (e.g. `[20:10, 21:00)`) must still be accepted. |

## Artifacts this rule touches
- `backend/src/main/java/com/serviceforge/service/TechnicianAvailabilityService.java` — `bookJob(...)` conflict check changed from exact start-time equality to true half-open interval overlap (`startTime.isBefore(existing.getEndTime()) && existing.getStartTime().isBefore(endTime)`). Extended in this pass to also apply the `TRAVEL_BUFFER_MINUTES` (45) buffer by treating each existing job as occupying `[start - buffer, end + buffer)` for conflict purposes: `startTime.isBefore(existing.getEndTime().plusMinutes(TRAVEL_BUFFER_MINUTES)) && existing.getStartTime().minusMinutes(TRAVEL_BUFFER_MINUTES).isBefore(endTime)`.
- `backend/src/test/java/com/serviceforge/controller/TechnicianAvailabilityControllerTest.java` — added tests covering identical range, start-inside-existing, fully-containing, end-inside-existing, and a genuinely non-overlapping booking that must still succeed. In this pass: updated `nonOverlappingRangeRespectingTravelBufferIsStillAccepted` to start at `20:10` (was `20:00`, which no longer respects the buffer) and added `rangeStartingLessThanBufferAfterExistingEndIsRejectedWithConflictError` and `rangeEndingLessThanBufferBeforeExistingStartIsRejectedWithConflictError`.
