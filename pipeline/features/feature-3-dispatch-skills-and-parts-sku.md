# Feature 3 — Dispatch Data Model: Technician Skills, Job Required Skill, Part SKU

| Field | Value |
|---|---|
| **Status** | Candidate-built / in progress |
| **One-line intent** | Extend the in-memory backend data model so technicians carry a list of skills, jobs carry a required skill, and parts exist with a SKU, all seeded in `MockDataStore` and exposed in REST JSON. |
| **Depends on** | `pipeline/decisions/feature-1-decisions.md` — **"standard travel buffer per job is 45 minutes"** (`TRAVEL_BUFFER_MINUTES = 45` in `TechnicianAvailabilityService`) and its amendment **"bookings use buffered interval conflict detection"** (a booking is rejected if its half-open `[startTime, endTime)` range overlaps an existing job for the same technician or sits less than 45 minutes before/after it; exactly 45 minutes is allowed). Both must remain unchanged; the constraint is enforced by rule `pipeline/feature2/rules/no-overlap-booking.md`. No dependency on Feature 2 (`feature-2-memory-pipeline.md`) — that feature touched only `pipeline/feature2/memory_pipeline/` and changed no backend/frontend code. |
| **In scope** | **Current state (verified before writing this spec):** `Technician` has `id`, `name`, `region`; `Job` has `id`, `technicianId`, `customerName`, `startTime`, `endTime`, `status` (all final except `status`); **no Part model exists anywhere** in `backend/` or `frontend/`; the only DTOs are `BookJobRequest` and `ApiError` — controllers return `Technician` and `Job` model objects directly and Jackson serializes them via getters.<br><br>**1. `Technician.skills`** — add `private List<String> skills` to `backend/.../model/Technician.java` with `getSkills()` and `setSkills(List<String>)`. Add a new constructor `Technician(Long id, String name, String region, List<String> skills)`; keep the existing 3-arg constructor (it initialises `skills` to an empty list). `getSkills()` never returns `null` (null input is stored as an empty list).<br><br>**2. `Job.requiredSkill`** — add `private final String requiredSkill` to `backend/.../model/Job.java` with `getRequiredSkill()`. Add a new 7-arg constructor ending in `String requiredSkill`; keep the existing 6-arg constructor (it sets `requiredSkill` to `null`). *Assumption A1:* no setter is added, because every other `Job` field except `status` is immutable; if a setter is required, a human must say so before step 2.<br><br>**3. `Part` model (new)** — *Assumption A2:* because no parts model exists, create `backend/.../model/Part.java` with the minimal fields `Long id` (final), `String sku`, `String name`, a 3-arg constructor, getters for all three, and setters for `sku` and `name`. In-memory only, with no quantity, stock, price, or job linkage.<br><br>**4. `MockDataStore` seed data** — add a `List<Part> parts` store with `getAllParts()` (unmodifiable) and `findPartBySku(String sku)` (`Optional<Part>`). Seed every existing record with the new fields (migration-safety rule 2):<br>• Technician 1 Alex Rivera / North → `["HVAC", "Electrical"]`<br>• Technician 2 Jordan Blake / South → `["Plumbing", "HVAC"]`<br>• Technician 3 Sam Okonkwo / East → `["Electrical", "Plumbing"]`<br>• Seeded job Acme Corp (tech 1) → `requiredSkill = "HVAC"`; Northwind Traders (tech 1) → `"Electrical"`; Globex (tech 2) → `"Plumbing"`. Each seeded job's skill is one its technician has.<br>• Parts (at least): `{1, "CMP-CLUTCH", "AC Compressor Clutch"}`, `{2, "FLT-16", "16x25x1 Air Filter"}`, `{3, "BRK-20A", "20A Single-Pole Circuit Breaker"}`, `{4, "VLV-BALL-075", "3/4in Brass Ball Valve"}`. SKUs are unique, non-blank, and uppercase.<br>Existing technician ids, names, regions, and seeded job times, customers, and statuses stay the same.<br><br>**5. REST exposure** — `GET /api/technicians`, `GET /api/technicians/{id}`, and `GET /api/technicians/{id}/jobs` automatically include `skills` / `requiredSkill` through the model getters. No response DTOs are introduced (*Assumption A3:* the intent's "REST API DTOs" is read as "the JSON shapes returned by the API", because the repo returns models directly). `BookJobRequest` gains an **optional** `String requiredSkill` with a getter and setter and no validation annotation. `POST /api/jobs` passes it through to the created `Job` and echoes it in the 201 response; if it is omitted, the result is `"requiredSkill": null`. `TechnicianAvailabilityService.bookJob(...)` gains an overload or an extra parameter to carry `requiredSkill`, and its conflict check stays **exactly** the same.<br><br>**6. Parts read endpoint** — *Assumption A4:* add a read-only `GET /api/parts` (new `PartController`, which delegates to a new `PartService` or equivalent service layer, with constructor injection, returning `ResponseEntity<List<Part>>`) so that `sku` can be seen in REST JSON. If a human rejects this, drop the endpoint and keep Part at the model and `MockDataStore` level only.<br><br>**7. Frontend models (types only)** — *Assumption A5:* to keep consumers in sync (migration-safety rule 3) without breaking existing Angular specs that build `Technician` literals without `skills`, add **optional** fields only: `skills?: string[]` in `frontend/src/app/models/technician.model.ts`, and `requiredSkill?: string \| null` on `Job` and `BookJobRequest` in `frontend/src/app/models/job.model.ts`. |
| **Out of scope** | • **Skill-based dispatch or matching.** This includes rejecting or warning when a technician lacks a job's `requiredSkill`, recommending or auto-assigning technicians by skill, and filtering `/api/technicians` by skill. This is the obvious next feature and must **not** be built here.<br>• **Parts reservation, stock, or inventory.** This includes quantity-on-hand, reserving parts against jobs, low-stock alerts, linking `Part` to `Job`, part pricing, and write endpoints for parts (`POST`/`PUT`/`DELETE /api/parts`).<br>• Any change to the conflict logic in `TechnicianAvailabilityService.bookJob(...)`, to `TRAVEL_BUFFER_MINUTES`, or to the 409/404 status mapping in `JobController`.<br>• Endpoints for editing technician skills or a job's required skill after creation.<br>• Validating skill values against a fixed list or enum (skills are free-form strings, stored as given), and validating `requiredSkill` in `BookJobRequest`.<br>• Angular UI changes: no rendering of skills, required skill, or parts, no new `Part` TS model, and no parts service/component.<br>• Renaming or removing any existing field, constructor, getter, or endpoint.<br>• Any real database or external service.<br>• Changes under `pipeline/feature2/memory_pipeline/`. |
| **Definition of Done** | **Model — Technician**<br>1. `Technician` has `getSkills()` / `setSkills(List<String>)` and a 4-arg constructor `(Long, String, String, List<String>)`. The old 3-arg constructor still compiles and produces `getSkills()` equal to an empty list, not `null`.<br><br>**Model — Job**<br>2. `Job` has `getRequiredSkill()` and a 7-arg constructor ending in `String requiredSkill`. The old 6-arg constructor still compiles and produces `getRequiredSkill() == null`.<br><br>**Model — Part**<br>3. `com.serviceforge.model.Part` exists with `getId()`, `getSku()`, `getName()`, `setSku(...)`, `setName(...)`, and a `(Long, String, String)` constructor.<br><br>**Seed data**<br>4. After startup, `MockDataStore.getAllTechnicians()` returns 3 technicians with the exact skills listed in In scope §4, and their ids, names, and regions are unchanged.<br>5. The 3 seeded jobs have `requiredSkill` values of `HVAC`, `Electrical`, and `Plumbing` as listed, and each is contained in its technician's `skills`.<br>6. `MockDataStore.getAllParts()` contains parts with SKUs `CMP-CLUTCH` and `FLT-16` (plus the other seeded SKUs). All SKUs are non-blank and unique, and `findPartBySku("FLT-16")` is present while `findPartBySku("NOPE")` is empty.<br><br>**REST JSON**<br>7. `GET /api/technicians` returns 200 and each element has a `skills` JSON array; technician 1's is `["HVAC","Electrical"]`.<br>8. `GET /api/technicians/1` returns 200 with `skills`; `GET /api/technicians/9999` still returns 404 with an `ApiError` `message`.<br>9. `GET /api/technicians/1/jobs` returns 200 and each seeded job has a `requiredSkill` key with its seeded value.<br>10. `POST /api/jobs` with `"requiredSkill": "HVAC"` returns 201 and `$.requiredSkill == "HVAC"`.<br>11. `POST /api/jobs` without `requiredSkill` (the existing request shape) returns 201 and `$.requiredSkill` is `null`.<br>12. (If A4 is approved) `GET /api/parts` returns 200 with a JSON array whose elements have `id`, `sku`, and `name`, including `sku == "CMP-CLUTCH"` and `sku == "FLT-16"`.<br><br>**Backward compatibility — 45-minute rule**<br>13. All existing tests in `TechnicianAvailabilityControllerTest` pass unmodified: identical range, start-inside, fully-containing, end-inside, `<45 min` after end (`19:40`), `<45 min` before start (`15:50`) → 409, and `20:10` → 201.<br>14. A new test shows that a booking with `requiredSkill` set is still rejected with 409 when it violates the 45-minute buffer, and is accepted when it respects it. This proves `requiredSkill` does not affect conflict detection.<br>15. `TRAVEL_BUFFER_MINUTES` is still `45` and the conflict expression in `bookJob(...)` is unchanged (diff check).<br><br>**Frontend and build**<br>16. The frontend TS interfaces contain the optional fields from In scope §7. The existing `technician.service.spec.ts` and `technician-calendar.component.spec.ts` pass without edits, and `npm test` / `ng build` succeed.<br>17. `mvn test` passes with zero failures, and no new Maven or npm dependency (including any database driver) is added. |
