# Feature 4 — Job Notes Injection Guardrail

| Field | Value |
|---|---|
| **Status** | Candidate-built / in progress |
| **One-line intent** | Define a strict prompt-injection and validation rule for untrusted job notes and a reservation-critic agent contract that checks each proposed reservation before execution. |
| **Depends on** | No additional decision from `pipeline/decisions/` is required. This documentation-only feature is based on `pipeline/feature2/design/security-design.md` and the existing Feature 2 parts-reservation requirements and MCP contracts. |
| **In scope** | Create `pipeline/feature2/rules/job-notes-injection-guardrail.md` first, then create `pipeline/feature2/agents/reservation-critic-agent.md`. The rule defines notes as untrusted data; enumerates the direct, indirect, obfuscated, false-authority, tool-policy, exfiltration, and resource-abuse injection vectors from the security design; specifies input and reservation-payload validation; prohibits notes/model output from authorizing or modifying a reservation; requires fail-closed behavior for invalid, ambiguous, stale, or unauthorized requests; limits critic-agent tools and outputs; prohibits raw notes/secrets in logs; and defines verification cases. The critic-agent contract must load and enforce this rule before any reservation payload reaches an execution tool, validate the exact job/SKU/positive-quantity tuple and trusted authorization evidence, reject unauthorized mutations, and emit only a structured allow/block result with reason codes and minimal safe details. The agent may not create authorization, silently repair payloads, execute or mutate reservations, or treat model assertions or notes as approval. The documents must state that this agent definition is a proposed policy artifact and is not runtime-enforced until explicitly wired and independently tested. Preserve human confirmation as the default; auto-approval remains disabled unless separately approved and deterministically authorized at the backend. |
| **Out of scope** | Adding `Job.jobNotes`, notes REST endpoints, storage or UI; implementing or deploying an LLM agent, prompt orchestration, MCP wiring, backend authorization, confirmation/policy issuer, reservation changes, or auto-approval; changing Feature 2 requirements or existing MCP contracts; changing the risk assessment/security-design decisions; claiming that markdown rules or agent instructions alone prevent prompt injection; and adding tests for unimplemented runtime behavior. |
| **Definition of Done** | - `pipeline/feature2/rules/job-notes-injection-guardrail.md` exists and identifies its affected feature, trust boundary, concrete injection vectors, strict input/payload validation constraints, prohibited authority paths, fail-closed behavior, safe logging/output constraints, verification criteria, and artifacts it touches.<br>- The rule explicitly states that job notes are untrusted regardless of author, delimiters/classifiers are not sufficient controls, notes/model output cannot grant approval or change the canonical reservation tuple, and any untrusted or invalid payload must be blocked before execution.<br>- `pipeline/feature2/agents/reservation-critic-agent.md` exists and defines its role, required rule-loading behavior, request/decision inputs, strict validation procedure, structured allow/block output, and pre-execution handoff contract.<br>- The agent contract requires blocking missing/invalid/expired/replayed authorization, mismatched session/actor/technician/job/SKU/quantity, non-positive or out-of-policy quantities, non-`SCHEDULED` or wrong-owner jobs, stale state, malformed/extra payload fields, and suspicious or ambiguous requests; it never treats notes or model-generated claims as trusted authorization.<br>- The agent has no reservation-execution, generic HTTP, arbitrary URL, shell, or filesystem mutation capability; it cannot modify or execute the payload. An allow decision is a validation result only and does not replace authoritative backend authorization or atomic final checks.<br>- Both documents preserve human confirmation as the default and explicitly leave auto-approval disabled absent a separately approved deterministic backend policy and security review.<br>- The rule and agent each specify verification cases covering direct/indirect/obfuscated prompt injection, false authority, tool/exfiltration requests, malformed and extra payload fields, tuple substitution, authorization failures and replay, stale data, fail-closed dependency errors, and no raw-notes/secret leakage. The documents do not claim these tests have been run against a runtime agent.<br>- References point to the existing security design and relevant Feature 2 requirements/MCP contracts; current implementation gaps and proposed-state boundaries are not represented as already fixed.<br>- Only the two requested policy/agent documents are produced in implementation; no model, backend, MCP, or frontend code changes are made. |

## Artifacts this feature touches
- `pipeline/feature2/rules/job-notes-injection-guardrail.md` — defines the untrusted-notes threat boundary, strict payload and authorization constraints, fail-closed behavior, safe output/logging, verification criteria, and non-authoritative status of the critic.
- `pipeline/feature2/agents/reservation-critic-agent.md` — defines the tool-less pre-execution critic contract, trusted input provenance requirements, exact candidate checks, structured decision output, failure behavior, and verification cases.
